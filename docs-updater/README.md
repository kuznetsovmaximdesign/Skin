# Локальный сервис обновления документации

Помогает техническому писателю обновлять существующие Markdown-документы: вы описываете, что
изменилось, сервис сам находит нужный документ, переписывает его **по вашему гайду по стилю** и
показывает наглядно, что именно поменялось.

Всё считается на вашем компьютере. Интернет не нужен: единственное сетевое обращение — к Ollama по
адресу `localhost:11434`. Никаких ключей, никаких облаков, ничего наружу не уходит.

Настройки по умолчанию рассчитаны на **MacBook на Apple Silicon (M3 Pro, 18 ГБ)**: небольшие модели,
короткое время жизни модели в памяти и работа моделей по очереди. Подробнее — в разделе
«Про память и скорость».

---

## Что понадобится один раз

1. **Python 3.10 или новее.** Проверить: `python3 --version`.
2. **Ollama** — программа, которая запускает модель локально. Скачивается с сайта ollama.com,
   ставится как обычное приложение.

## Установка (5 шагов, копируйте команды по одной)

```bash
# 1. Перейти в папку сервиса
cd docs-updater

# 2. Создать отдельное окружение для Python (чтобы ничего не сломать в системе)
python3 -m venv .venv

# 3. Включить это окружение
source .venv/bin/activate          # macOS / Linux
# .venv\Scripts\activate           # Windows (PowerShell)

# 4. Поставить зависимости
pip install -r requirements.txt

# 5. Скачать модели для Ollama (один раз, качается несколько гигабайт)
ollama pull qwen3:4b               # модель, которая пишет текст (~2,5 ГБ)
ollama pull bge-m3                 # модель, которая ищет нужный документ (~1,2 ГБ)
```

Если хочется текст получше и не жалко скорости, на 18 ГБ поместится и модель побольше:
`ollama pull qwen3:8b`, затем впишите `qwen3:8b` в поле «Модель генерации» на странице.
Если, наоборот, память нужна для другого, вместо `bge-m3` возьмите более лёгкую
`ollama pull nomic-embed-text`.

## Запуск (каждый раз)

```bash
# 1. Запустить Ollama (в отдельном окне терминала; часто он уже работает сам)
ollama serve

# 2. В папке docs-updater запустить сервис
source .venv/bin/activate
uvicorn backend.main:app --reload --port 8000
```

Открыть в браузере: **http://localhost:8000**

Остановить сервис — `Ctrl + C` в терминале.

## Как пользоваться (то, что видно на странице)

**Шаг 1. Папка с документацией.** Укажите папку, где лежат ваши `.md` файлы, и нажмите
«Переиндексировать». Сервис прочитает документы, разобьёт их на разделы и запомнит их смысл —
это нужно, чтобы потом находить нужный документ по описанию. Повторяйте после того, как файлы
поменялись: второй и следующие разы проходят быстро, потому что пересчитываются только изменённые
куски текста.

**Шаг 2. Правила и образцы.** Здесь два способа объяснить сервису, как должны выглядеть документы.

*Правила словами.* Загрузите свой `.md`-гайд или отредактируйте текст прямо на странице. Можно
подложить **несколько файлов правил** (например, общий гайд и правила бренда) — все они обязательны.
Если ваша правка противоречит правилам, побеждают правила, а спорное место помечается `[спорно: …]`.

*Образцы — сервис изучит формат сам.* Подложите готовые документы, которые считаете эталонными, и
нажмите «Изучить формат». Сервис разберёт их: порядок разделов, обращение на «вы», длину предложений
и абзацев, маркеры списков, оформление команд и дат, регистр заголовков. Галочка «дополнить правилами
от модели» добавляет к этому формулировки от локальной модели.

**Обучение делается один раз.** Результат сохраняется в `data/derived-guide.md` и дальше
подмешивается в каждую правку автоматически — ничего заново подкладывать не нужно. Его видно на
странице («Формат изучен по образцам…»), можно посмотреть текст, временно выключить галочкой
или забыть кнопкой. Явные правила из файлов всегда главнее изученного формата.

**Шаг 3. Что изменилось.** Опишите словами: что поменялось или какой функционал появился.
Нажмите «Найти подходящий документ» — сервис покажет 3–5 кандидатов с процентом совпадения.
Верхний выбирается сам, любой можно выбрать мышкой или взять документ из списка вручную. Заодно
поиск сам подставит наиболее подходящий раздел в шаге 4 — его всегда можно поменять.

**Выбор продукта** — в шапке страницы, если продуктов несколько. Всё на странице (индекс, поиск,
правки, результаты) относится к выбранному продукту.

**Шаг 4. Обновление.** Сначала выберите, что править: весь документ целиком или один раздел из
списка. Правка одного раздела надёжнее и быстрее — остальной текст модель вообще не видит, значит
не может его испортить. Кнопка «Обновить по гайду» отправляет модели выбранный текст, ваше описание
и гайд. Текст появляется на экране **сразу, по мере того как модель его пишет**, — ждать вслепую не
нужно, видно и скорость, и что именно получается. Где данных не хватило, будет пометка `[уточнить]`,
а рядом с результатом — счётчик таких мест.

**Шаг 5. Что поменялось.** Здесь три вкладки:

- **Было / стало** — сравнение по абзацам: удалённые слова подсвечены красным, добавленные —
  зелёным. Галочка «только изменения» прячет нетронутые абзацы.
- **Превью с подсветкой** — документ в читаемом виде, как он будет выглядеть после правки:
  заголовки, списки, таблицы и код отрисованы, а всё новое подсвечено зелёным. Галочка
  «показывать удалённые куски» дополнительно показывает то, что пропало.
- **Исходный текст** — результат целиком в виде Markdown. Текст **можно править руками**
  (например, дописать то, что модель пометила как `[уточнить]`) и нажать «Сохранить мои правки»:
  сравнение и превью пересчитаются, а правки уйдут в тот же отдельный файл.

Кроме «Обновить по гайду» есть кнопка **«Предложить правки по разделам»**: сервис показывает каждую
правку отдельно — что было, что станет, цитата из вашего описания, которая её требует, и уверенность.
Каждую можно принять или отклонить (с комментарием — он запомнится), а потом нажать «Собрать документ
из принятых»: незатронутые разделы останутся прежними.

В шаге 3 рядом с поиском есть ещё две кнопки: **«Все затронутые статьи»** (что нужно дополнить,
заменить или считать устаревшим) и **«На что ещё посмотреть»** (битые ссылки, устаревшие значения,
следы удалённого, оставшиеся пометки). В шаге 1 — **«Построить карту документов»**.

Дальше:
- «Проверить по гайду» — модель ещё раз сверяет готовый текст с гайдом и выписывает нарушения
  списком (нужен подключённый гайд);
- «Скачать обновлённый .md» — забрать файл;
- «Заменить оригинал» — записать поверх исходного файла (только по вашему клику, и рядом
  автоматически сохраняется копия старой версии с именем вида `api-auth.md.bak-20260818-120000`).

**Оригинал никогда не перезаписывается сам.** Результат всегда сначала попадает в отдельный файл в
папке `data/output/`. Все сохранённые результаты видны внизу страницы в блоке «Сохранённые
результаты»: там написано, из какого документа и по какому описанию сделана каждая версия, — оттуда
их можно скачать позже. Файлы никогда не затирают друг друга, даже если сделать
два обновления подряд.

После нажатия «Заменить оригинал» индекс обновляется автоматически, так что поиск сразу знает новый
текст документа.

## Правила портала: папка `docs-config/`

Правила берутся из четырёх файлов в `docs-config/` (в корне репозитория) — это **источник
правды**. Изменили файл — изменились правила, код править не нужно.

| Файл | Что задаёт |
| --- | --- |
| `article-type-schemas.json` | типы статей: обязательные секции, порядок, уровни заголовков, метаполя по профилям |
| `markdownlint-rule-candidates.md` | стандартные коды markdownlint и список кастомных правил `KDOC-*` с уровнями |
| `glossary.csv` | термбанк: термин → принятое написание → чего избегать → перевод / «не переводить» |
| `report.md` | контекст разбора для людей; сервис его не разбирает |

Что загружено, видно на странице в блоке «Правила портала» (типы статей, профили, кастомные правила
с их уровнями, размер глоссария) и в `GET /api/docs-config`. Оттуда же собирается словарь Vale и
запускается сверка языковых версий. Форматы описаны в `docs-config/README.md`.

### Профили шаблона

Портал неоднороден: поколения шаблона сосуществуют, а у Online Help и Knowledge Base
различается даже формат метаданных. Поэтому у документа есть **профиль** —
`legacy_help`, `modern_help` или `modern_kb`. Он берётся из front-matter
(`template_profile`) или определяется эвристикой: есть front-matter — новое поколение,
признаки базы знаний — `modern_kb`, метаданные только в подвале — старое поколение.
Правила одного профиля к другому не применяются.

### Тип статьи

Тип берётся из front-matter (`type_id`) или определяется по структуре: заголовкам, началу
названия, характерным словам. Документ проверяется по схеме **своего** типа. Тип
`api_reference_external` не гоняется через текстовый линтер: детальный API живёт во
внешнем Swagger-инструменте, и сервис помечает такую статью как «вне области текстовой
проверки».

### Кастомные правила `KDOC-*`

Отдельный проход, не стандартные коды markdownlint. Каждое правило включается и
отключается, привязано к типу и/или профилю:

- тип врезки только по машиночитаемому маркеру (`> [!NOTE]`) — **никогда по цвету**;
- лид-ин «Чтобы …:» и абзац-результат в инструкциях;
- полужирные названия элементов интерфейса;
- таблица вместо списка при трёх и более однотипных пунктах;
- блок метаданных в подвале статьи;
- расшифровка аббревиатуры при первом употреблении (кроме терминов глоссария);
- alt-текст и подпись у изображения;
- наличие `article_id` для сверки языковых версий.

Уровни можно менять в `config.yaml`:

```yaml
checks:
  kdoc:
    KDOC-TABLE-FOR-PARALLEL: error   # поднять рекомендацию до нарушения
    KDOC-ESCALATION: off             # выключить правило
```

**Нарушение или рекомендация.** Спорные выводы разбора (обязателен ли раздел эскалации,
таблица вместо списка — требование или совет) по умолчанию идут как **рекомендации** и
не считаются ошибками. Поднять их до нарушений можно в конфиге, когда команда
документации это подтвердит.

### Глоссарий → словарь Vale

`POST /api/docs-config/sync-glossary` собирает из `glossary.csv` словари для Vale:
принятые написания, список запрещённых и правила замен «избегать X → использовать Y».
Продуктовые имена (KUMA, Kaspersky CompanyAccount) помечаются как «не переводить» и
остаются как есть во всех локалях. Неточный эквивалент термина в другой локали ошибкой
не считается.

### Сверка языковых версий

`GET /api/crosslocale` сопоставляет статьи по `article_id` и проверяет **раздельно**:

- структурный паритет — совпадает ли форма документа (состав и порядок уровней
  заголовков; сами заголовки переведены, поэтому дословно не сравниваются);
- рассинхрон дат и версий — совпадение структуры не означает, что версии обновляли вместе.

Отсутствие версии на каком-то языке по умолчанию не считается расхождением: часть статей
рыночно-специфична. Включается флагом `languages.require_all_targets`.

Эти же находки попадают в общий список «На что ещё посмотреть» (`POST /api/drift`).

## Автоматическая проверка соответствия

Модель соблюдает правила «на словах» ненадёжно, поэтому каждый результат ещё и проверяется машинно —
по трём осям сразу:

1. **Формулировка** — запрещённые слова, принятые написания и глоссарий, длина предложений,
   пассивный залог. Правила лежат в `data/style-rules.yaml`, их правит редактор, а не программист.
2. **Оформление** — иерархия заголовков, единые маркеры списков, язык у блоков кода, длина строк,
   лишние пустые строки, пробелы в конце.
3. **Шаблон статьи** — обязательные разделы и их порядок, уровни заголовков, поля front-matter,
   alt-текст у картинок, допустимые типы врезок. Описан в `data/template.schema.yaml`.

Найденные нарушения передаются модели конкретным списком с требованием исправить (до двух заходов,
настраивается `max_fix_iterations`). Починка принимается, только если нарушений стало меньше.
Всё, что осталось, показывается писателю списком под результатом — ничего не прячется.

Проверить произвольный текст можно и отдельно: `POST /api/check`.

### Vale и markdownlint (необязательно)

Встроенные проверки работают всегда и ничего не требуют. Если хотите полноценные линтеры, поставьте
их локально — сервис подхватит их сам и добавит их находки к своим:

```bash
brew install vale                 # проверка прозы
npm install -g markdownlint-cli2  # проверка разметки
```

Конфигурация уже лежит в проекте: `.vale.ini` со стиль-пакетом `styles/Corp/` (запрещённые слова,
замены, длина предложений) и словарём `styles/config/vocabularies/Corp/`, а также
`.markdownlint.jsonc`. Оба инструмента работают офлайн; если их нет в системе, сервис молча
обходится встроенными правилами.

## Сопровождение: правки как код-ревью

Кроме «переписать документ целиком» есть режим, в котором сервис ведёт себя как ревьюер:

- **Правки по разделам с обоснованием.** `POST /api/changeset/propose` подбирает затронутые
  разделы по описанию изменения и предлагает правку для каждого. У каждой правки есть цитата из
  вашего описания, которая её требует. Если модель хочет тронуть то, что описанием не обосновано,
  правка помечается как **предположение** и получает низкую уверенность — молча она не проходит.
- **Принимаете по одной.** `POST /api/changeset/{id}/decide` — принять или отклонить конкретную
  правку с комментарием. `POST /api/changeset/{id}/build` собирает документ **только из принятых**;
  остальные разделы остаются байт-в-байт. Оригинал по-прежнему не трогается.
- **Отклонения запоминаются.** Они пишутся в локальный `data/feedback.jsonl` и подмешиваются в
  следующие запросы к модели как «прошлые правила-исправления от писателя», чтобы отклонённое
  не предлагалось снова. Посмотреть: `GET /api/feedback`.

## На что ещё посмотреть: детект расхождений

`POST /api/drift` (можно с описанием изменения) собирает офлайн-сигналы по всей папке:

- битые внутренние ссылки и якоря (в несуществующие файлы и заголовки);
- устаревшие значения: если изменение вводит «120 минут», найдутся места, где написано «60 минут»;
- упоминания того, что по описанию убрали или переименовали;
- термины вне глоссария;
- оставшиеся пометки `[уточнить]`, `TODO`, `[спорно: …]`.

## Карта «документ ↔ что он документирует»

`POST /api/map/build` один раз считает для каждого документа короткую справку: что он описывает и
какие сущности затрагивает. Справка хранится в индексе и используется при выборе целевого документа —
поиск опирается на смысл, а не только на совпадение слов. Пересчитывается только для изменившихся
документов. Посмотреть карту: `GET /api/map`.

## Регресс-проверки (golden-кейсы)

```bash
python -m tests.golden_run          # офлайн, с локальной заглушкой Ollama
python -m tests.golden_run --live   # с настоящими моделями из config.yaml
```

Кейсы лежат в `tests/golden/cases.yaml`: документ + описание изменения → какие разделы должны быть
затронуты, что обязано появиться и исчезнуть, чист ли текст по проверкам, валидны ли ссылки и
остались ли нетронутые разделы дословно прежними. Прогон печатает «пройдено/провалено» по каждому
кейсу. Выбор нужного раздела проверяется только в режиме `--live`: у офлайн-заглушки векторы
игрушечные.

## Новая статья по шаблону продукта

На странице для этого есть блок «Новая статья по шаблону»: название, тип статьи, профиль шаблона и
поле требований. Через API — `POST /api/article/new`. Черновик собирается из технических требований. Сервис не пишет
свободный текст: он берёт разделы из шаблона продукта (`data/template.schema.yaml`), их порядок и
уровни, и заполняет каждый по требованиям. Факты — только из требований; где данных нет, ставится
`[уточнить]`. Ближайшая существующая статья используется как образец тона (факты из неё не берутся).
Черновик проходит тот же цикл «проверил → починил», что и обычные правки, и сохраняется отдельным
файлом в `data/output/`.

## Какие статьи затронуты изменением

`POST /api/impact` — не одна статья, а все затронутые. Кандидаты подбираются по карте
«документ ↔ что он документирует» и по разделам, затем каждая получает класс **дополнить /
заменить / устарело**, оценку релевантности и причину. Список отсортирован по релевантности.

## Несколько продуктов

У каждого продукта своя папка документации, свои гайды и шаблон, свой индекс и свои результаты.
Настраивается в `config.yaml` в разделе `products`; поля, которых у продукта нет, наследуются из
общих настроек. Во всех запросах продукт указывается параметром `?product=<id>`:

```bash
curl -X POST "http://localhost:8000/api/reindex?product=beta"
curl -X POST "http://localhost:8000/api/search?product=beta" -d '{"query":"..."}'
```

Поиск, автосвязывание, правки и генерация одного продукта физически не видят документы, гайды и
шаблоны другого. Список продуктов: `GET /api/products`.

## Языковые версии (15 языков)

Одна логическая статья — это N файлов на разных языках (`docs/<язык>/путь` или `имя.<язык>.md`,
задаётся `languages.layout`). Правка делается на языке-источнике, затем отдельным шагом
переносится на остальные версии:

На странице каскад запускается кнопкой «Перевести на другие языки» рядом с результатом; список
версий показывает, какие готовы, а какие помечены как требующие вычитки. Через API:

```bash
curl -X POST http://localhost:8000/api/cascade -d '{"doc_path": "api-auth.md"}'
```

- Термины держатся едиными через общий термбейз `data/glossary.yaml` — тот же, что использует
  проверка формулировок.
- Каждая языковая версия проходит проверку соответствия. Если для языка заведён свой файл правил
  (`data/style-rules.<язык>.yaml`), используется он.
- Языки из `languages.low_resource` помечаются как **требующие ручной вычитки**: открытые модели на
  них слабее, и такие версии отдаются как черновики, а не как готовый результат. То же происходит,
  если проверка нашла нарушения.
- Результаты сохраняются отдельными файлами; оригиналы языковых версий не перезаписываются.

Состояние версий одной статьи: `GET /api/languages?doc_path=...`.

## Публикация в Confluence и на портал

Единый источник правды — файл сервиса; из него документ уходит на обе площадки сразу.

На странице — кнопка «Опубликовать…»: сначала показывается превью со списком площадок и тем, что
будет создано, а что обновлено, и только потом появляется кнопка подтверждения. Через API:

```bash
curl -X POST http://localhost:8000/api/publish/preview -d '{"doc_path": "api-auth.md"}'
curl -X POST http://localhost:8000/api/publish -d '{"doc_path": "api-auth.md", "confirm": true}'
```

- **Только по подтверждению.** Без `confirm: true` не отправляется ничего; превью показывает
  площадки, адреса, что будет создано, а что обновлено.
- **Идемпотентность.** Соответствие «документ ↔ страница Confluence ↔ статья портала» хранится в
  `data/publications.json`; повторная публикация обновляет ту же страницу.
- **Настройки — в конфиге, доступы — в переменных окружения.** В `config.yaml` только адреса и имена
  переменных (`CONFLUENCE_TOKEN`, `PORTAL_TOKEN`); токенов в файлах проекта нет.
- По умолчанию публикация **выключена**: сервис остаётся полностью офлайновым.

## Конфиденциальность требований, доступ и аудит

- **Внутренний контур полностью локален.** Требования, инференс, эмбеддинги и индексы не покидают
  компьютер: единственный сетевой адрес — `localhost:11434`. Онлайн-моделей нет даже как запасного
  варианта.
- **Проверка перед выпуском наружу.** Публикация проходит через проверку: документ с пометкой
  `classification: confidential`, лежащий в конфиденциальных путях или содержащий признаки
  функциональных требований, наружу не уходит — запрос отклоняется с объяснением.
- **Аудит без содержимого.** Каждое обращение к модели и каждая публикация пишутся в
  `data/audit.jsonl`: время, событие, роль, документ, модель, результат. Текстов и требований в
  журнале нет — только отпечаток и длина. Смотреть: `GET /api/audit`.
- **Доступ по Рутокену и роли.** При `security.auth: rutoken` каждый запрос должен нести отпечаток
  сертификата с аппаратного токена в заголовке `X-Rutoken-Thumbprint`; отпечаток отображается в роль.
  Роль ограничивает доступные продукты и уровни секретности: поиск не выдаёт документы, которые роли
  видеть не положено. По умолчанию режим выключен — сервис локальный и открыт.

## Про память и скорость (Apple Silicon, 18 ГБ)

Сервис специально сделан бережным к памяти:

- **Модели работают по очереди.** Перед генерацией сервис просит Ollama выгрузить модель поиска,
  перед поиском и индексацией — модель генерации. Две модели одновременно в памяти не висят.
  Отключается флагом `sequential_models: false` в `config.yaml`.
- **`keep_alive: "5m"`.** Ollama держит модель в памяти пять минут после запроса, потом освобождает.
- **Документация не грузится в память целиком.** Индексация идёт по одному файлу: файл читается,
  режется на разделы, эмбеддинги считаются небольшими батчами (`embed_batch: 8`) и сразу пишутся
  в базу. Поиск тоже читает индекс по строкам, а не целиком.
- **Индекс — SQLite-файл** `data/index.sqlite3`, векторы лежат бинарно. Ничего внешнего не нужно.
- **`num_ctx: 8192`** — компромисс для `qwen3:4b`. Если документы длинные и памяти хватает,
  поднимите до 16384; если документ не помещается, сервис прямо об этом скажет.

GPU (Metal) Ollama задействует сам — настраивать ничего не нужно.

## Настройки: `config.yaml`

```yaml
ollama:
  generation_model: "qwen3:4b"   # модель, которая пишет текст
  embedding_model: "bge-m3"      # модель, которая ищет документ
  keep_alive: "5m"               # сколько модель живёт в памяти после запроса
  sequential_models: true        # не держать обе модели в памяти разом
paths:
  docs_dir: "data/docs"          # папка с вашей документацией
  style_guide: "data/styleguide.md"
```

Те же четыре поля меняются прямо на странице в шаге 1 — файл обновится автоматически.
Пути можно писать коротко (`data/docs`) или полностью (`/Users/me/Documents/docs`).

Если конфигов несколько (например, для разных проектов), нужный указывается при запуске:

```bash
DOCS_UPDATER_CONFIG=/путь/к/другому/config.yaml uvicorn backend.main:app --port 8000
```

## Если что-то пошло не так

| Что видно на странице | Что делать |
| --- | --- |
| «Ollama не отвечает» | Запустите `ollama serve` или откройте приложение Ollama |
| «Нет моделей: qwen3:4b» | Выполните `ollama pull qwen3:4b` |
| «Индекс пуст» | Нажмите «Переиндексировать» в шаге 1 |
| «В папке нет файлов .md» | Проверьте путь к папке документации в шаге 1 |
| Ответ ждёт очень долго | Возьмите модель поменьше (`qwen3:4b` вместо `qwen3:8b`) или увеличьте `request_timeout` в `config.yaml` |
| Компьютер начал заметно тормозить | Проверьте, что `sequential_models: true`, и уменьшите `num_ctx` в `config.yaml` |
| «Документ и гайд не помещаются в окно модели» | Увеличьте `generation.num_ctx` в `config.yaml` или сократите гайд — иначе модель не увидит документ целиком |

## Проверка автотестами

```bash
source .venv/bin/activate
pip install pytest
python -m pytest tests -q
```

Тесты не обращаются к настоящему Ollama — вместо него поднимается локальная заглушка, поэтому
их можно запускать вообще без интернета. Что проверяется: индексация, поиск нужного документа,
обновление текста, diff, скачивание, замена оригинала с резервной копией, понятные сообщения при
выключенном Ollama и отсутствующей модели. Отдельные тесты следят за тем, что ни в коде сервиса,
ни на странице нет ни одного внешнего адреса.

Есть ещё проверка страницы в настоящем браузере — она проходит весь путь кликами и следит, чтобы
браузер не сделал ни одного запроса наружу:

```bash
pip install playwright && playwright install chromium
python -m pytest tests/test_browser.py -q
```

Без playwright этот тест просто пропускается.

1. Отключите Wi-Fi и сетевой кабель.
2. Запустите `ollama serve` и сервис (`uvicorn backend.main:app --port 8000`).

Всё работает: страница не загружает ни шрифтов, ни скриптов из сети, а модель крутится локально.
